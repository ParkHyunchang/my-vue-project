## 구현 결과

1. 주문·데이터 신뢰성: 국내 주문 전송 후 응답 불명은 UNKNOWN으로 보존하고 신규·직접·정정 주문을 차단한다. 취소는 허용하며 증권사 체결 대조 전 자동 해제하지 않는다. 주문 금액 곱셈 오버플로를 차단했다. 국내/미국 화면용 계좌 조회는 위험 상태 저장 등 매매 루프의 부작용과 분리했다.
2. 수기 기록: 계좌 목록 또는 개별 계좌 조회가 실패하면 합계·손익·비중 계산을 보류한다. 매입가 누락은 손익 범위를 표시하며, 중복 클릭·늦게 도착한 AI/시장 응답을 방어한다. 로컬 자료 자동 POST/삭제를 없애고 출처 확인 후 명시적으로 가져오도록 변경했다. 성공 항목은 사용자별로 추적하고 원본을 보존한다.
3. 계좌 구조: 증권사·별칭·운용 목적별 수기 계좌를 추가/수정한다. 기존 네 계좌는 가상 legacy 키로 노출하며 기존 보유 API·자료를 그대로 유지한다. 신규 계좌는 소수 8자리 수량/평단가와 사용자·계좌별 소유권을 검증한다. 증권사 선택은 API 연결을 의미하지 않는다.
4. 모바일: 운영 제어·최근 이벤트·갱신/조회 오류를 앞쪽에서 확인하고 위험 정책·연구/전략 설정·상세 로그는 펼쳐보도록 정리했다. 계좌 동기화가 주문 취소/청산 관리까지 수행할 수 있음을 버튼 주변과 확인창에 표시한다.

## API / 데이터 호환성

- `/api/portfolio/accounts`: GET 목록, POST 신규 수기 계좌. `/{accountKey}` PUT 메타데이터 수정.
- `/{accountKey}/holdings`: GET/POST, `/{holdingId}` PUT/DELETE, `/{holdingId}/core` PUT. 로그인 및 기존 portfolio 메뉴 권한, 사용자/계좌 소유권 검사. 다른 사용자의 계좌는 404, 유효하지 않은 입력은 400, 동일 계좌 종목 중복은 409.
- 응답의 `holdingsPath`로 기존 네 계좌와 신규 계좌를 구분한다. 새 계좌 source는 MANUAL. 키움 조회 합계와 합치지 않는다.
- 신규 테이블 `portfolio_account`, `portfolio_account_holding`만 추가한다. 기존 네 보유 테이블은 변경/복사/삭제하지 않는다. 기존 정수 수량 API는 소수 입력을 잘라 저장하지 않고 거부한다.
- 새 계좌의 전체 AI 진단과 새 계좌 포함 통합 AI 진단은 기존 네 계좌만 분석하는 서버의 범위 오류를 막기 위해 비활성화했다. 종목별 분석은 유지한다.

## 검증

- FE: 최종 격리 21 suites / 214 tests PASS. 전체 lint PASS. production build PASS(기존 번들 크기/Browserslist 경고). 마지막 취소 버튼의 secondary CSS 보완은 대상 lint PASS.
- BE: JDK21 격리 Maven 369 tests, 실패/오류 0, 기존 선택 테스트 3 skip. 대상 Java Spotless 적용, 양쪽 diff check PASS.
- H2에서 실제 신규 엔티티 저장/재조회, 소수 수량·평단가, 사용자/계좌 격리, 중복 종목, legacy 메타데이터 변경 시 기존 데이터 보존 검증.
- 합성 API 브라우저: 390px 계좌 생성 및 탭 이동, 신규 계좌 빈 상태, 삼성 합성 종목 0.125→0.375 수정 확인. 320px 수기/국내·미국 자동매매 화면 가로 넘침 없음. 일부 계좌 503 주입 후 전체 합계 차단·재시도 안내를 320px 및 1280px에서 확인했다.
- 브라우저 시험은 `scripts/stock-accounts-review-api.cjs` 및 `serve:isolated`의 loopback 합성 자료만 사용했다. 실계좌/운영 DB/실주문에 쓰지 않았다. 실제 Android 기기와 증권사 응답은 미검증이다.

## 배포와 남은 조건

- 미커밋·미배포. 배포 시 BE → FE 순서. NAS의 ddl-auto=update 환경은 신규 테이블 생성 여부를 확인한다. validate 환경은 BE의 `create_portfolio_account_tables.sql`을 사전 검토/적용해야 한다. 운영 DB에는 이번에 적용하지 않았다.
- 되돌릴 기준은 FE 6be8be3, BE 41decc7. 롤백 시 새 테이블은 남겨 신규 기록을 보존한다.
- 삼성·신한의 실제 자동 조회는 공식 지원 경로/계약 확보 후 진행한다. 현재 신청 없음이며 연결 완료로 표시하지 않는다.
- 로컬 가져오기의 동일 사용자 여러 탭 동시 실행은 서버 idempotency가 없어 중복 가능성이 남는다. 단일 화면의 중복 클릭/부분 실패 재시도는 방어했다. 후속으로 서버 가져오기 키를 도입한다.
- UNKNOWN 주문은 증권사 내역과 대조하여 상태를 확정하는 운영 절차가 필요하다. 불명 상태를 임의로 성공/실패로 바꾸는 자동 해제 기능은 제공하지 않는다.

## 2026-11-24 삼성·신한 실제 연결 추가 요청 조사

사용자가 실제 자동 조회 연결을 요청하여 총괄·기획·검증이 공식 경로를 다시 확인했다. 기존 미커밋 소스는 보존했으며 이번 조사로 실연동 코드/운영 설정을 변경하지 않았다. 실제 연결 상태는 여전히 미완료다.

- 신한 [i indi 공식 안내](https://www.shinhansec.com/siw/customer-center/channel/channel_homeTrading-indi/contents.do): 사용계약 신청, 프로그램/인터페이스 문서 확보가 선행된다. Windows ActiveX 방식이며 NAS 직접 실행 사양이 아니다. Windows 조회 전용 중계를 후보로 검토할 수 있다. 현재 공개 자료에서 국내 잔고 TR의 정확한 필드 계약 및 미국주식 잔고 지원은 확정하지 못했다.
- [신한 FAQ](https://www.shinhansec.com/siw/customer-center/channel/channel_homeTrading-indi_faq/contents.do): 최초 잔고 TR 뒤 실시간 잔고/체결을 사용하도록 안내한다. 단순 주기적 전체 조회 방식은 과다 조회 제한을 고려해야 한다.
- 삼성: 공식 공개 검색에서 개인용 잔고 API의 신청 경로/기술 명세를 확보하지 못했다. API가 존재하지 않는다고 단정하지 않는다. 국내·미국 보유종목/예수금/평균단가를 개인 웹서비스에서 조회할 수 있는 공식 경로의 증권사 확인이 필요하다.
- [CODEF 공식 소개서](https://codef.io/assets/pdf/202307_CODEF_API_%EC%86%8C%EA%B0%9C%EC%84%9C.pdf)는 증권 종합자산 조회와 정식 서비스 신청 시 사업자·프로젝트 정보/운영 검토 절차를 설명하지만 2023년 자료다. 현재 개인 비사업자 이용과 삼성·신한 미국 종목별 잔고 지원은 별도 확인해야 한다.
- [Octover 공식 API](https://developer.octover.co.kr/apis/K002/AA001)는 삼성/신한 전계좌 조회를 나열하지만 증권-기업 상품이다. 개인 종목별 국내·미국 잔고 연동을 충족한다고 간주하지 않는다.
- 다음 단계는 신한 사용계약/정확한 잔고 명세 확보, 삼성 공식 또는 승인된 제공자의 개인 사용 및 국내·미국 범위 확인이다. 인증 정보는 채팅/저장소에 수집하지 않는다. 문서만으로 모의 어댑터를 작성해 실제 연결 완료로 표시하지 않는다.

## 커밋·운영 배포 요청

사용자가 삼성·신한 연결 조건은 직접 확인하기로 하고, 구현된 변경의 커밋·배포를 명시 요청했다. BE `eef56e0`을 main에 푸시했다. FE는 BE 배포 성공을 확인한 후 푸시한다. 위 미배포 표시는 이 요청 이전의 상태이며 실제 완료 여부는 해당 SHA의 GitHub Actions 결과와 완료 보고를 따른다. 운영 docker 프로파일의 ddl-auto=update 설정을 확인했다. 기존 보유 자료를 이관하거나 삭제하는 SQL은 실행하지 않는다.
